00 / FOUNDATIONS

How matrix multiplication works

A matrix is a rectangular grid of numbers. Multiplication combines a row from the first grid with a column from the second.

TRY THE MATHChoose a cell in C
THE RULE

Multiply pairs. Add them up.

For every output cell, walk across one row of A and down one column of B. Multiply matching numbers, then add those products. In our program, all three matrices are square: N rows and N columns.

C[row, col] = Σ A[row, k] × B[k, col]

The symbol Σ means “add up,” and k visits positions 0 through N−1. There are N² outputs, each taking N multiply-and-add steps: about 2N³ floating-point operations.

THE STORAGE

A grid on screen. A line in memory.

C++ stores our matrices as flat arrays. Row-major means all of row 0 comes first, followed by row 1, and so on. To find a cell, skip row × N numbers, then advance col more.

index = row * N + col
0,00,10,21,01,11,2…

Reading adjacent addresses is usually more efficient than jumping far apart. Most of our optimizations build on this observation.

01 / THE IMPLEMENTATIONS

Build the kernel, one step at a time

Each chapter starts from the code in the one before it. Read the short explanation, try the exercise, then check the part of the code that changed. Some versions will be slower for certain matrix sizes; that is useful information too.

Small code details that also affect performance

__restrict__: this promises the compiler that the relevant pointer accesses do not alias through other pointers in a conflicting way. Our A, B, and C use separate allocations. Such information can enable better generated code; it is a promise the caller must honor, not a runtime check.

Templates and constexpr: tile sizes known at compile time let the compiler generate specialized kernels for T=8, 16, and 32. These are three compiled variants, not one runtime loop deciding its tile width at every iteration.

#pragma unroll: a short fixed loop can be expanded into repeated instructions. This can remove loop-control work and expose independent operations, but may increase code size and register use. Unrolling does not add threads or reduce the required arithmetic.

Optimization flags: -O3 enables optimized compilation, while -lineinfo helps profilers map instructions back to source lines. The Windows build script also passes host /O2. Use the same build settings when comparing runs.

Error handling and validation: checking CUDA calls and comparing results do not accelerate the multiply. They make optimization trustworthy. The correctness check accepts finite outputs within 1e-3 + 1e-3 × abs(reference). The test suite uses a double-accumulation oracle; normal benchmark runs compare against basic CPU FP32.

REUSING INPUT VALUES

Why does register tiling help here?

At N=2048, the register kernel takes 2.9375 ms, compared with 14.1269 ms for naïve CUDA. A thread computes several outputs and reuses its input values instead of loading a separate pair for every product.

There is also enough work to spread across the GPU: the register kernel launches 1,024 blocks at this size. Select N=256 in the profiling section to see what happens when that grid contains only 16 blocks.

CHOOSING A TILE SIZE

Shared16 and shared32 are close.

Shared16 took 7.8344 ms; shared32 took 7.7041 ms. Shared32 is about 1.7% faster in this run despite lower theoretical occupancy. Shared32 reuses values across more outputs, while shared16 can keep more warps resident.

Repeated samples and profiling are needed to separate a stable difference from run-to-run variation. More resident warps, more reuse, and fewer synchronization phases are different trade-offs.

CPU BASELINE CONTEXT

Read the CPU baseline carefully

The separate basic CPU reference took 28,820.6 ms, while the timed basic CPU average was 96,611.3122 ms (about 96.61 seconds per multiply). Both execute the same algorithm. Temperature, power state, other work, or code/build changes could contribute; this output cannot identify the cause.

Use the GPU baseline when comparing CUDA kernels. The difference between the CPU reference pass and the timed CPU average needs investigation before treating the CPU-to-GPU speedup as representative. These CPU implementations use one thread; an optimized CPU library would be a different comparison.

How were these numbers measured?

The CPU uses std::chrono::steady_clock. GPU timings use CUDA events around repeated launches after a warm-up and correctness check. GPU inputs are already on the device: allocation, input/output copies, and validation are excluded. CPU timing includes clearing C for variants that accumulate into it.

The separate CPU reference pass took 28,820.6 ms; it is a validation pass, not another timed implementation row. Throughput uses 2 × N³ / (milliseconds × 10⁶). At N=2048 the conventional count is 17,179,869,184 floating-point operations. A fused multiply-add counts as two operations.

All variants passed the program’s finite-value and absolute-plus-relative tolerance check. “0.0000” is rounded output; it does not establish mathematical exactness. Fifty iterations produce an average, not a variability estimate or a causal diagnosis. These speedups describe compute time, not full application latency or a comparison against an optimized multithreaded CPU library.

04 / THREADS & OCCUPANCY

How many blocks can an SM keep resident?

Occupancy asks how many warps can be resident on a streaming multiprocessor (SM), relative to its maximum. It does not measure useful work completed.

GRID

The whole assignment

A grid is all the blocks launched for one kernel.

⊃
BLOCK

A cooperating team

A block runs on one SM. Its threads share memory and barriers.

⊃
WARP

32 execution lanes

A block is divided into groups of 32 threads.

⊃
THREAD

One worker

A thread owns its indices and private working values.

A GPU has many SMs. Each has a limited supply of registers, shared memory, and slots for threads and blocks. Bigger blocks or more resources per block can reduce how many blocks fit at once. Having several warps available helps the SM find work when others wait for data.

READ THE NUMBERS TOGETHER

Occupancy tells us how much work can fit, not how fast it finishes

The printed figures imply a 48-warp limit per SM. A 1,024-thread shared32 block has 32 warps; one resident block gives 32 / 48 ≈ 66.67%. The register kernel fits five 256-thread blocks: 5 × 8 / 48 ≈ 83.33%.

These are resource-based upper bounds. A small grid may not supply enough blocks to reach them across the GPU. Compare these limits with the measured occupancy in the profiling section. The two numbers answer different questions: how many warps could fit, and how many were actually resident during execution.

05 / EXPERIMENTS TO TRY

Try a change and explain the result

Once you can explain the existing kernels, try changing one detail. Keep the input, precision, and timing method fixed so that the result is easier to interpret.

  1. 01

    Check correctness at the edges.

    Run --test. It covers sizes including 17, 33, 65, and 513, where tiles are incomplete, plus identity and zero inputs. GPU output is filled with NaNs before validation to expose missed stores.

  2. 02

    Give the GPU a larger problem.

    Choose several sizes between 64 and 4096, including a size such as 513 that does not divide evenly into a tile. Repeat the experiment and compare the timing ranges. The profiling harness provides ten warm-up launches per trial; the simple teaching executable provides one.

  3. 03

    Profile a selected kernel.

    Use Nsight Compute to inspect achieved occupancy, global memory traffic, shared memory bank conflicts, and stall reasons. Run Compute Sanitizer for memory errors, races, and barrier misuse. These checks are not established by the timing output alone.

  4. 04

    Ask whether transfers change the answer.

    Add a separate end-to-end measurement from input transfer to returned output. If the data starts on the CPU and the matrices are small, transfer and launch costs can change the practical benefit of GPU acceleration.
