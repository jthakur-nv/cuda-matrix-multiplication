00 / FOUNDATIONS

First, what are we computing?

A matrix is a rectangular grid of numbers. Multiplication combines a row from the first grid with a column from the second.

TRY THE MATHChoose a cell in C
THE RULE

Multiply pairs. Add them up.

For every output cell, walk across one row of A and down one column of B. Multiply matching numbers, then add those products. In our program, all three matrices are square: N rows and N columns.

C[row, col] = Σ A[row, k] × B[k, col]

The symbol Σ means “add up,” and k visits positions 0 through N−1. There are N² outputs, each taking N multiply-and-add steps: about 2N³ floating-point operations.

THE STORAGE

A grid on screen. A line in memory.

C++ stores our matrices as flat arrays. Row-major means all of row 0 comes first, followed by row 1, and so on. To find a cell, skip row × N numbers, then advance col more.

index = row * N + col
0,00,10,21,01,11,2…

Reading adjacent addresses is usually more efficient than jumping far apart. Most of our optimizations build on this observation.

A RESULT TO INVESTIGATE

Shared16 took 0.8836 ms.

That is roughly 12× the naïve GPU time. Keep the measurement in the record, but one average from five iterations cannot explain its cause. Scheduling, clock changes, launch gaps, or genuine kernel behavior are possibilities—not established findings.

Repeat the same case with more warm-up launches, more iterations, and larger matrices before drawing a performance conclusion.

WHY “MORE OPTIMIZED” CAN LOSE

Small problems change the trade-off.

At N=256, a matrix contains just 65,536 floats (256 KiB). A and B together occupy 512 KiB. Cache reuse may already help the naïve kernel. Shared memory adds loads and barriers; register tiling increases per-thread work and resource use.

The register kernel launches only 16 output blocks at this size. It exposes less block-level parallelism than shared32’s 64 blocks. These are reasons to investigate, not proof of the measured slowdown.

How were these numbers measured?

The CPU uses std::chrono::steady_clock. GPU timings use CUDA events around repeated launches after a warm-up and correctness check. GPU inputs are already on the device: allocation, input/output copies, and validation are excluded. CPU timing includes clearing C for variants that accumulate into it.

The separate CPU reference pass took 9.0894 ms; it is a validation pass, not another timed implementation row. Throughput uses 2 × N³ / (milliseconds × 10⁶). At N=256 the conventional count is 33,554,432 floating-point operations. A fused multiply-add counts as two operations.

All variants passed the program’s finite-value and absolute-plus-relative tolerance check. “0.0000” is rounded output; it does not establish mathematical exactness. A single small run is not a controlled GPU performance study. These speedups describe compute time, not full application latency or a comparison against an optimized multithreaded CPU library.

03 / THREADS & OCCUPANCY

A full room isn’t always a fast room.

Occupancy asks how many warps can be resident on a streaming multiprocessor (SM), relative to its maximum. It does not measure useful work completed.

GRID

The whole assignment

A grid is all the blocks launched for one kernel.

⊃
BLOCK

A cooperating team

A block runs on one SM. Its threads share memory and barriers.

⊃
WARP

32 execution lanes

A block is divided into groups of 32 threads.

⊃
THREAD

One worker

A thread owns its indices and private working values.

A GPU has many SMs. Each has a limited supply of registers, shared memory, and slots for threads and blocks. Bigger blocks or more resources per block can reduce how many blocks fit at once. Having several warps available helps the SM find work when others wait for data.

Shared32 has 66.67% theoretical occupancy—and the best custom time here.

The printed figures imply a 48-warp limit per SM. A 1,024-thread shared32 block has 32 warps; one resident block gives 32 / 48 ≈ 66.67%. The register kernel fits five 256-thread blocks: 5 × 8 / 48 ≈ 83.33%.

These are resource-based upper bounds. A small grid may not supply enough blocks to reach them across the GPU. Actual achieved occupancy requires profiling, and memory efficiency and work per instruction still matter.

04 / THE NEXT EXPERIMENT

Measure. Explain. Then optimize.

The first run is a starting point. Change one variable at a time and keep the precision and timing scope consistent.

  1. 01

    Check correctness at the edges.

    Run --test. It covers sizes including 17, 33, 65, and 513, where tiles are incomplete, plus identity and zero inputs. GPU output is filled with NaNs before validation to expose missed stores.

  2. 02

    Give the GPU a larger problem.

    Try N=512, 1024, and 2048. Repeat runs, increase iterations, and compare medians across runs. The current harness has one warm-up per variant; extend it to several warm-ups for a more stable study. The CPU reference becomes expensive at large N.

  3. 03

    Profile a selected kernel.

    Use Nsight Compute to inspect achieved occupancy, global memory traffic, shared memory bank conflicts, and stall reasons. Run Compute Sanitizer for memory errors, races, and barrier misuse. These checks are not established by the timing output alone.

  4. 04

    Ask whether transfers change the answer.

    Add a separate end-to-end measurement from input transfer to returned output. If the data starts on the CPU and the matrices are small, transfer and launch costs can change the practical benefit of GPU acceleration.
